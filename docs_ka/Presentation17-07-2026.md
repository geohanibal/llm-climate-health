# ახსნის გეგმა ხელმძღვანელებთან პრეზენტაციისთვის

## 0. მთავარი წამყვანი ხაზი

> "LLM აქ არ არის oracle, რომელიც ცოდნას თხზავს — ის არის ინტერფეისის/გამჭვირვალობის ფენა, რომელიც ჩაშენებულ, ვალიდირებულ, დახურულ ETL ლოგიკას აქცევს ხელმისაწვდომად non-expert მომხმარებლისთვის."

ეს ფრაზა ღირს დასამახსოვრებელი — ხელმძღვანელების ტიპური კითხვა იქნება "სად აქვს LLM-ს ნამდვილი როლი და სად რისკია?", და ეს პასუხი ყველა დანარჩენს აწესრიგებს.

## 1. გახსნა — პრობლემა და მოტივაცია (~2 წუთი)

- დაავადებების გადამტანები (კოღოები) მგრძნობიარენი არიან ტემპერატურის/ნალექის მიმართ → კლიმატური მონაცემი = early indicator.
- პრობლემა practice-ში: ეს მონაცემები სხვადასხვა ფორმატით, სხვადასხვა გარჩევადობით (დღიური vs თვიური vs წლიური), სხვადასხვა API-დან მოდის — ჰარმონიზაცია ხელით რთული და შეცდომისკენ მიდრეკილი პროცესია.
- შენი წვლილი: ზოგადი (disease-/region-agnostic) პლატფორმა, სადაც non-expert მომხმარებელი ბუნებრივი ენით აღწერს მოთხოვნას და იღებს analysis-ready, ჰარმონიზებულ dataset-ს — **არა პროგნოზს**, არამედ downstream მოდელირებისთვის მზა input-ს.
- ვალიდაციის შემთხვევა: დენგე ტაილანდში (OpenDengue + ERA5), არქიტექტურა გავრცობადია მალარიაზე/ქოლერაზეც (უკვე მიბმულია WHO GHO-ს მეშვეობით).

## 2. არქიტექტურის ახსნა (~2-3 წუთი)

დახატე/ახსენე 3 ფენა (დიაგრამა უკვე მზადაა `docs_ka/dokumentacia.tex`-ში — შეგიძლია იქიდან PDF გამოიღო და ეკრანზე დადო):

1. **Frontend** — Flutter Web (ერთი კოდი web/mobile/desktop-ისთვის, არჩეული ხელმისაწვდომობის გამო).
2. **Backend** — FastAPI/Python: validation, ETL orchestration, cache, rate-limit.
3. **გარე წყაროები** — კლიმატის API-ები (Open-Meteo/ERA5, NASA POWER, TMD ტაილანდისთვის), დაავადების არქივები (OpenDengue, WHO GHO, HDX), + Gemini LLM.

აღნიშნე: ერთი Docker image, backend ემსახურება frontend-საც — deployment-ის სიმარტივე ბაკალავრიატის ვადებში ღირებული ინჟინერული გადაწყვეტილება.

## 3. ცოცხალი დემო — ნაბიჯ-ნაბიჯ სცენარი (~7-10 წუთი, ყველაზე მნიშვნელოვანი ნაწილი)

1. **ბუნებრივი ენა → ფორმის შევსება**: ჩაწერე მაგ. "Dengue in Thailand, 2015 to 2023, monthly, temperature and precipitation" → აჩვენე, LLM-ს როგორ ავალდებულებს დახურულ ლექსიკონს (მხოლოდ დაშვებული disease/region/variable სიებიდან), და თუ რამე ამოცნობილი არაა → ცარიელი ველი + `notes`-ში ახსნა, არა halucinated მნიშვნელობა.
2. **წყაროების ცოცხალი ძებნა** — "wow moment": დააჭირე disease source search-ს, აჩვენე რომ ეს WHO GHO/HDX-ის რეალურ, ცოცხალ API call-ს უკავშირდება — LLM აქ **არ** მონაწილეობს URL-ის ან citation-ის გამოგონებაში.
3. **Run integration** — აჩვენე pipeline steps ტექსტურად (transparency), შემდეგ explanation card — ახსენე `explanation_source: llm/fallback` მექანიზმი.
4. **Data Audit Log** — თუ custom URL/upload გამოიყენე, გახსენი audit modal — column fuzzy-matching, გაწმენდილი/გაფილტრული სტრიქონები.
5. **გრაფიკი + KPI ბარათები** — toggles ჩართო/გამორთო series, აჩვენე dual-axis adaptive scaling.
6. **სტატისტიკური ანალიზი** — ეს ახალი და ძალიან ღირებული ნაწილია დემოსთვის: Pearson/Spearman + **lagged cross-correlation** (lag 0-3 თვე) — ახსენე *რატომ* lag: კოღოს გამრავლების ციკლი ნალექს/ტემპერატურას გარკვეული დაგვიანებით მოსდევს, ამიტომ disease(t) vs climate(t-lag) უფრო ბიოლოგიურად საფუძვლიანია, ვიდრე lag-0 კორელაცია. აჩვენე `scientific_disclaimer` — single-point vs spatial მონაცემი, არა causal inference.
7. **Population/incidence rate** — თუ ჩართული, აჩვენე World Bank/UN WPP-ზე დაფუძნებული incidence per 100k — ეს country-შორის შედარებადობას აძლევს საშუალებას.
8. **Export** — CSV/JSON + PDF report ჩამოტვირთვა.

## 4. საკვანძო ტექნიკური გადაწყვეტილებები, რომლებიც უნდა გამოკვეთო

ეს ის ნაწილია, სადაც ხელმძღვანელები ამოწმებენ "ინჟინერულ სიმწიფეს" და არა მხოლოდ დემოს:

- **"Fill, never run" პრინციპი**: LLM-ს არასდროს აქვს ETL-ის გაშვების უფლება — მხოლოდ ფორმის prefill. მომხმარებელი ყოველთვის ადასტურებს ხელით.
- **დახურული ლექსიკონი + re-validation backend-ში**: LLM-ის პასუხი ისევ ხელახლა მოწმდება კოდში (`_coerce_parsed_json`) — halucination ვერასდროს მიაღწევს ETL-მდე.
- **წყაროების ძებნა LLM-ის გარეშე**: მხოლოდ 2 სანდო API (WHO GHO, HDX) — არა ღია web search, სანდოობის გამო.
- **გამჭვირვალობა**: pipeline steps, `explanation_source`, `last_verified` timestamp, audit log — ყველგან ჩვეულია "აჩვენე რა მოხდა ნამდვილად", არა black box.
- **Resilience**: cache (15 წუთი), rate-limiting Gemini-ზე, fallback explanation, ცნობილი შეცდომების 502/400 მკაფიო დაბრუნება 500-ის ნაცვლად.

## 5. სავარაუდო კითხვები + პასუხის ჩარჩო

| შესაძლო კითხვა | პასუხის ბირთვი |
|---|---|
| "რატომ LLM და არა უბრალო hardcoded ლოგიკა?" | LLM მხოლოდ interpretation/explanation ფენაზეა (non-expert access + transparency) — ნამდვილი მონაცემთა გადაზიდვა/join დეტერმინისტული, ტესტირებული კოდია. |
| "როგორ ვართ დარწმუნებული სისწორეში?" | დახურული ლექსიკონი, re-validation, source citation ყოველთვის ეკრანზე, audit log, scientific disclaimer. |
| "რამდენად განზოგადებადია სხვა დაავადება/რეგიონზე?" | Malaria/cholera უკვე WHO GHO-ს მეშვეობით მიბმულია; region registry ზოგადია, disease-agnostic დიზაინით. |
| "ეს causal კავშირს ამტკიცებს?" | არა — ეს EDA/data-prep ხელსაწყოა; disclaimer ცალსახად ამბობს, რომ საჭიროა subnational spatial disaggregation causal inference-ისთვის. |
| "რა არის შემდეგი ეტაპი?" | (იხ. ქვემოთ). |

## 6. შეზღუდვები/შემდეგი ნაბიჯები — თავად დაასახელე პირველი

ეს ნდობას აძლიერებს (self-awareness ნიშანი), ვიდრე ხელმძღვანელს დაასახელებინო:

- TMD (ტაილანდის მეტეო) response-ის ველების სახელები დოკუმენტაციიდანაა აღდგენილი, ჯერ არ არის smoke-tested რეალურ credentials-ზე.
- ამჟამად ერთი წარმომადგენლობითი წერტილი რეგიონზე — gridded მონაცემები დაგეგმილია.
- მომავალი emission scenario პროგნოზები (CMIP6/CORDEX) + bias correction ჯერ არ არის ინტეგრირებული — მხოლოდ historical reanalysis.
- Job queue/background processing გრძელვადიანი მოთხოვნებისთვის ჯერ არ არსებობს.

## 7. დახურვა

დაუბრუნდი §0-ის მთავარ ხაზს და შეაჯამე: მუშა end-to-end სისტემა (frontend→backend→3+ climate წყარო→2 disease-source catalog→LLM ახსნა→სტატისტიკა→export), თუმცა შეგნებული, დასახელებული საზღვრებით.
